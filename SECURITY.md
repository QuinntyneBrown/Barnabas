# Security Policy

## Reporting a vulnerability

**Please do not report security vulnerabilities through public GitHub issues, pull requests, or
discussions.**

Report them privately through GitHub's private vulnerability reporting:

> **[Report a vulnerability](https://github.com/QuinntyneBrown/Barnabas/security/advisories/new)**

That form is visible only to the maintainers. If you cannot use it, open a public issue containing
**no detail** — the words "I would like to report a security issue privately" are enough — and a
maintainer will arrange a private channel.

### What to include

The more of this you can give us, the faster we can confirm and fix it:

- The kind of issue — cross-tenant read, authorisation bypass, injection, path traversal, denial of
  service, disclosure of personal data, and so on.
- The endpoint or screen, and the file and line if you have them.
- Step-by-step instructions to reproduce it, including the role and congregation of the actor.
- A proof of concept, if you have one.
- What an attacker gets out of it.

### What to expect

| | |
|---|---|
| Acknowledgement | Within **3 working days** |
| Initial assessment | Within **10 working days**, including whether we consider it a vulnerability and its severity |
| Fix or mitigation | Depends on severity; we will tell you the target and keep you updated |
| Credit | You will be credited in the advisory unless you ask not to be |

We will keep you informed while we work, and we will tell you before we publish. Please give us a
reasonable opportunity to fix the issue before disclosing it publicly.

## Supported versions

Barnabas has not yet cut a release. Security fixes are made against `main`, and until a version is
tagged, `main` is the only supported version.

| Version | Supported |
|---|---|
| `main` | ✅ |

## Scope

### In scope

Anything that breaches one of the guarantees below, or any of the criteria under `L1-014` (tenant
isolation) and `L1-015` (security and data protection) in
[`docs/specs/L2.md`](docs/specs/L2.md).

### Out of scope

- Findings that require an attacker to already hold a valid moderator or administrator session in
  the congregation they are attacking. Those roles are trusted by design; **privilege escalation
  into them is very much in scope.**
- Anything in the **Development** environment only. `DevelopmentController` exposes a database
  reset and reads back dispatched sign-in links; it is removed from the application model outside
  Development by `RemoveDevelopmentEndpoints`, and the seeded members and signing keys in
  `appsettings.Development.json` are marked as not for any deployment.
- Reports generated by an automated scanner with no demonstrated impact.
- Missing hardening headers on a response that already carries a Content Security Policy forbidding
  inline script, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, a referrer policy, and
  HSTS.
- Denial of service by volume against a developer machine.

## What Barnabas guarantees

These are the properties an exploit would have to break. Each is asserted by acceptance tests; the
criteria are in [`docs/specs/L2.md`](docs/specs/L2.md).

### The congregation boundary

Every read and every write is constrained to the congregation named in the caller's signed token.
The boundary is held in two places, and they answer different questions:

- The **`DbSet` accessors fail closed.** Treating an absent congregation as "no filter" would turn
  every anonymous endpoint into a cross-tenant read, so the accessor raises rather than returning
  unfiltered rows.
- The **global query filter** supplies the predicate once a congregation is known. It is applied by
  reflection over the model, so an entity is covered the moment it implements `ITenantOwned` rather
  than when somebody remembers to add it.

A resource in another congregation answers **404, never 403** — a refusal would confirm the thing
exists. A moderator's role widens what they may *do*, never what they can *see*.

Three stores bypass the filter deliberately and are documented as such: `IAuthenticationStore`
(sign-in happens before a congregation is known), `IProvisioningStore`, and `IInvitationStore`
(redeeming an invite is anonymous).

### Authentication and sessions

- **No passwords.** Identity is possession of the mailbox. Barnabas stores no password and no
  password hash.
- **Access tokens are short-lived** — fifteen minutes by default, and the criterion caps them at
  sixty.
- **Refresh tokens rotate on use**, by a conditional update whose affected-row count is the answer,
  so two callers racing produce one winner and one `401` rather than two valid tokens.
- **The session is read on every authenticated request**, because a signature cannot express
  revocation. Sign-out is immediate rather than eventual, and a member's role and status are
  restamped from their record each request — so an approval or a moderator grant takes effect on
  the next visit rather than the next sign-in.
- **Sign-in links are throttled**, five per address per fifteen minutes, and so is invite
  redemption. Both answer `429` with `Retry-After`.

### Member-supplied content

- **Text is stored as it was typed and returned encoded.** The JSON encoder is declared rather than
  inherited, so a description containing a script tag cannot close one in any document the response
  is embedded in.
- **Every query is parameterised**, and search wildcards are escaped — a search for `%` matches a
  percent sign, not everything.
- **Payment, delivery, and deposit fields are refused by name** on every member-authored endpoint,
  rather than accepted and dropped. A caller who sent a card number is told it was not taken.

### Uploaded files

- **The bytes that arrive are never the bytes that are stored.** Every rendition is decoded and
  re-encoded from pixels, so no EXIF block, GPS tag, or colour profile survives — the metadata is
  not stripped so much as never carried across.
- **Three checks guard the decoder, in this order**: the declared type is compared with the actual
  bytes; the dimensions are read from the header and bounded *before* a pixel is allocated, because
  a 400 KB file can declare a canvas that decodes to gigabytes; and only then is it decoded. All
  three answer `415` with the same message — saying which would tell somebody probing the endpoint
  how close they got.
- **Nothing under the photo root is served as static content.** Bytes leave through an endpoint that
  names its own content type, with `nosniff`.
- **Photo identifiers are capability URLs**: unguessable version-4 GUIDs, issued to the uploader and
  disclosed only inside a congregation's own responses, served with `Cache-Control: private`. This
  is the product's one deliberate anonymous read, and the reasoning is recorded in
  [`docs/slices/slice-9-photos-and-hardening.md`](docs/slices/slice-9-photos-and-hardening.md).

### Personal data

- **No endpoint describing another member returns an email address.** This is a property of the
  projections, not a rule somebody has to remember — those types have no field to put one in.
- **A member can export everything held about them**, and only what they wrote: the other party's
  messages are the other party's data.
- **A member can ask to be forgotten.** Their profile, listings, and messages are irreversibly
  anonymised in place — not deleted, because the surviving party's thread has to stay legible — and
  every session they hold ends, on every device. Their photographs are deleted outright. The erased
  address is derived, never hashed: a hash of a known address is a lookup table away from being the
  address again.

### Telemetry

Logs carry no email address, no message body, and no listing description. A validation failure
records the field name and never the offending value. An error surfaced to a client carries no
stack trace and no internal identifier. A caller-supplied correlation identifier is length-bounded
and character-restricted before it is written down, because a newline in one is how a forged entry
becomes two convincing ones.

## Secrets

The signing keys and connection strings in `appsettings.Development.json` and in the acceptance
suites are literal development values and are named as such. **A deployment must supply its own**
`Jwt:SigningKey` and `Database:ConnectionString` through configuration or a secret store. Finding
the development key in the repository is not a vulnerability; finding a real one is — please report
it.
