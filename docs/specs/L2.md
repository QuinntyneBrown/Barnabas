# L2 - Detailed Requirements

Every requirement traces to exactly one L1. Every acceptance criterion is tagged with the
suite that owns it:

- **[API]** — a backend integration test in `backend/tests/Barnabas.IntegrationTests`.
- **[E2E]** — a Playwright test in `frontend/tests/e2e`, driving the UI through page objects.

Each test file shall carry a trace comment naming the requirements it covers. The comment is
not optional; it is how coverage is verified.

```typescript
// Acceptance Test
// Traces to: L2-006, L2-011
// Description: Redeeming a valid invite code creates a member awaiting approval
```

---

## L2-001: Provision a congregation
**Traces to:** L1-001

An administrator shall be able to create a congregation with a display name and a URL-safe
slug. The slug shall be unique across the deployment and immutable once set.

**Acceptance Criteria:**
1. [API] Given no congregation with the slug `st-aidans`, when an administrator posts a congregation with that slug, then it is created and returned with an identifier.
2. [API] Given a congregation with the slug `st-aidans`, when an administrator posts another with the same slug, then the response is 409 Conflict and no second congregation is created.
3. [API] Given an existing congregation, when an administrator attempts to change its slug, then the response is 400 Bad Request and the slug is unchanged.
4. [API] Given a caller who is not an administrator, when they post a congregation, then the response is 403 Forbidden.

---

## L2-002: Configure the neighbourhoods of a congregation
**Traces to:** L1-001

Each congregation shall carry its own ordered set of neighbourhood names. Members select
their neighbourhood from this set; free text shall not be accepted.

**Acceptance Criteria:**
1. [API] Given a congregation, when an administrator sets its neighbourhoods to a list of names, then those names are returned in the order supplied.
2. [API] Given a congregation whose neighbourhoods do not include `Rosedale`, when a member sets their neighbourhood to `Rosedale`, then the response is 400 Bad Request naming the field.
3. [E2E] Given a member editing their profile, when they open the neighbourhood control, then only their own congregation's neighbourhoods are offered.

---

## L2-003: Designate moderators
**Traces to:** L1-001

A member of a congregation shall be able to hold the moderator role. Moderator authority
applies only within the congregation that granted it.

**Acceptance Criteria:**
1. [API] Given an approved member, when an administrator grants them the moderator role in their congregation, then subsequent moderation requests from that member succeed.
2. [API] Given a member who is not a moderator, when they request the moderation queue, then the response is 403 Forbidden.
3. [E2E] Given a signed-in moderator, when they open the You screen, then a moderator tools entry is shown.
4. [E2E] Given a signed-in member who is not a moderator, when they open the You screen, then no moderator tools entry is shown.

---

## L2-004: Present the congregation's name throughout the interface
**Traces to:** L1-001

The congregation's display name shall appear wherever the board is identified, so a member
always knows which congregation they are looking at.

**Acceptance Criteria:**
1. [E2E] Given a member of a congregation named `St. Aidan's`, when they open the board, then the heading names that congregation.
2. [E2E] Given a member of a congregation named `St. Mark's`, when they open the board, then the heading names `St. Mark's` and never another congregation.

---

## L2-005: Issue an invite code
**Traces to:** L1-002

A moderator shall be able to issue an invite code for their congregation. A code shall be at
least six characters, drawn from an unambiguous alphabet, and carry an expiry date.

**Acceptance Criteria:**
1. [API] Given a moderator, when they issue an invite code, then a code of at least six characters and an expiry date are returned.
2. [API] Given two codes issued in the same congregation, when they are compared, then they differ.
3. [API] Given a member who is not a moderator, when they issue an invite code, then the response is 403 Forbidden.

---

## L2-006: Redeem a valid invite code
**Traces to:** L1-002

Redeeming an unexpired, unredeemed code shall begin the joining flow for the congregation
that issued it.

**Acceptance Criteria:**
1. [API] Given an unexpired, unredeemed code for `St. Aidan's`, when it is redeemed, then the response identifies `St. Aidan's` and the joining flow is begun.
2. [E2E] Given a valid code, when a prospective member submits it on the join screen, then the profile screen is shown.
3. [API] Given a code that has been redeemed once, when the same code is redeemed again, then the response is 410 Gone.

---

## L2-007: Reject an unrecognised invite code
**Traces to:** L1-002

An unrecognised code shall be rejected without revealing whether any similar code exists.

**Acceptance Criteria:**
1. [API] Given a code that was never issued, when it is redeemed, then the response is 404 Not Found and no member is created.
2. [E2E] Given an unrecognised code, when a prospective member submits it, then the invalid-code screen explains the code was not recognised and offers to try another.
3. [API] Given an unrecognised code and an expired code, when each is redeemed, then neither response reveals which of the two conditions applied beyond its status code.

---

## L2-008: Reject an expired invite code
**Traces to:** L1-002

A code past its expiry date shall not be redeemable.

**Acceptance Criteria:**
1. [API] Given a code whose expiry date has passed, when it is redeemed, then the response is 410 Gone and no member is created.
2. [E2E] Given an expired code, when a prospective member submits it, then the invalid-code screen explains the code has expired and names who to ask for another.

---

## L2-009: Reject an already-redeemed invite code
**Traces to:** L1-002

A code shall be redeemable once only.

**Acceptance Criteria:**
1. [API] Given a code already redeemed, when it is redeemed again, then the response is 410 Gone and no second member is created.
2. [API] Given a code redeemed concurrently by two callers, when both requests complete, then exactly one succeeds and the other receives 410 Gone.

---

## L2-010: Supply a profile while joining
**Traces to:** L1-002

A prospective member shall supply a display name and neighbourhood before their request to
join is submitted. Help tags and a description are optional.

**Acceptance Criteria:**
1. [API] Given a redeemed code, when a profile is submitted with a display name and a valid neighbourhood, then a member is created in the pending state.
2. [API] Given a redeemed code, when a profile is submitted without a display name, then the response is 400 Bad Request naming the field and no member is created.
3. [E2E] Given the profile screen, when a member submits it without a display name, then an error is shown against that field and the screen is not left.

---

## L2-011: Await moderator approval
**Traces to:** L1-002

A member in the pending state shall not see the board, and shall be told their request is
with the congregation's moderators.

**Acceptance Criteria:**
1. [API] Given a member in the pending state, when they request the board, then the response is 403 Forbidden.
2. [E2E] Given a member who has just submitted their profile, when the submission succeeds, then the awaiting-approval screen is shown and it names the congregation.
3. [E2E] Given a pending member, when they sign in, then the awaiting-approval screen is shown rather than the board.

---

## L2-012: Request a sign-in link
**Traces to:** L1-003

A member shall be able to request a single-use sign-in link sent to their registered email
address. The system shall never store a password.

**Acceptance Criteria:**
1. [API] Given an approved member's email address, when a sign-in link is requested, then the response is 202 Accepted and a link is dispatched to that address.
2. [API] Given any member record, when it is inspected, then it holds no password or password hash field.
3. [E2E] Given the sign-in screen, when a member submits their email address, then the check-your-email screen is shown and it names the address the link was sent to.
4. [API] Given an anonymous caller, when a sign-in link is requested, then the member lookup succeeds without a congregation context, and no listing, request, or thread is readable on that request.

---

## L2-013: Do not disclose whether an email address is registered
**Traces to:** L1-003

The sign-in response shall be identical whether or not the address belongs to a member, so
the endpoint cannot be used to enumerate members.

**Acceptance Criteria:**
1. [API] Given an unregistered email address, when a sign-in link is requested, then the response is 202 Accepted with the same body and timing characteristics as for a registered address, and no link is dispatched.
2. [E2E] Given an unregistered address, when a member submits it, then the check-your-email screen is shown, identical to the registered case.

---

## L2-014: Exchange a sign-in link for a session
**Traces to:** L1-003

Following a valid sign-in link shall issue a JWT bound to the member and their congregation.

**Acceptance Criteria:**
1. [API] Given an unexpired, unused sign-in token, when it is exchanged, then a JWT is issued carrying the member identifier, the congregation identifier, and the member's role.
2. [API] Given an issued JWT, when it is presented to an authenticated endpoint, then the request succeeds as that member.
3. [E2E] Given a member following a valid sign-in link, when the page loads, then the board is shown.
4. [API] Given a sign-in token exchanged successfully, when the issued token is inspected, then its congregation claim matches the congregation on the member record and not any value supplied by the caller.
5. [API] Given a sign-in token exchanged successfully, when the issued token is inspected, then it carries a session identifier, and a token carrying no session identifier is refused.

---

## L2-015: Expire a sign-in link
**Traces to:** L1-003

A sign-in token shall expire no more than 15 minutes after issue.

**Acceptance Criteria:**
1. [API] Given a sign-in token issued 16 minutes ago, when it is exchanged, then the response is 410 Gone and no session is created.
2. [API] Given a sign-in token issued 1 minute ago, when it is exchanged, then a session is created.
3. [E2E] Given an expired sign-in link, when a member follows it, then a screen explains the link has expired and offers to send another.

---

## L2-016: Make a sign-in link single use
**Traces to:** L1-003

A sign-in token shall be consumed on first exchange.

**Acceptance Criteria:**
1. [API] Given a sign-in token already exchanged once, when it is exchanged again, then the response is 410 Gone and no second session is created.
2. [API] Given a sign-in token exchanged concurrently by two callers, when both complete, then exactly one session is created.

---

## L2-017: Rate-limit sign-in link requests
**Traces to:** L1-003

Requests for sign-in links shall be limited per address and per source to prevent mailbox
flooding.

**Acceptance Criteria:**
1. [API] Given five sign-in link requests for one address within 15 minutes, when a sixth is made, then the response is 429 Too Many Requests and no further link is dispatched.
2. [API] Given a rate-limited address, when 15 minutes have elapsed, then a further request succeeds.

---

## L2-018: Expire and renew a session
**Traces to:** L1-003

A session shall expire after a bounded lifetime and shall be renewable without a further
email round trip while it remains valid.

**Acceptance Criteria:**
1. [API] Given a JWT past its expiry, when it is presented, then the response is 401 Unauthorized.
2. [API] Given a valid, unexpired session, when renewal is requested, then a new token is issued and the previous refresh token is invalidated.
3. [E2E] Given a member whose session has expired, when they open the board, then the sign-in screen is shown.
4. [API] Given one refresh token presented concurrently by two callers, when both complete, then exactly one rotation succeeds and the other receives 401 Unauthorized.
5. [API] Given a member holding two active sessions, when one is renewed, then the other remains usable.

---

## L2-019: Sign out
**Traces to:** L1-003

A member shall be able to end their session, after which their tokens shall no longer be
accepted.

**Acceptance Criteria:**
1. [API] Given a signed-in member, when they sign out and then present the same refresh token, then the response is 401 Unauthorized.
2. [E2E] Given a signed-in member on the You screen, when they choose to sign out and confirm, then the public landing screen is shown.
3. [E2E] Given a member who has signed out, when they navigate back to the board, then the sign-in screen is shown.
4. [API] Given a signed-in member, when they sign out and then present the access token issued for that session, then the response is 401 Unauthorized.
5. [API] Given a session whose refresh token has been rotated at least once, when the member signs out and presents the most recent access token, then the response is 401 Unauthorized.
6. [API] Given a member signed in on two devices, when they sign out on one, then the session on the other remains usable.

---

## L2-020: View own profile and settings
**Traces to:** L1-004

A member shall be able to see their own profile and settings on one screen.

**Acceptance Criteria:**
1. [API] Given a signed-in member, when they request their own profile, then their display name, neighbourhood, description, and help tags are returned.
2. [E2E] Given a signed-in member, when they open profile and settings, then their current name, neighbourhood, description, and help tags are shown populated.

---

## L2-021: Edit own profile
**Traces to:** L1-004

A member shall be able to change their display name, neighbourhood, description, and help
tags, and shall be told the change was saved.

**Acceptance Criteria:**
1. [API] Given a signed-in member, when they submit a changed display name, then the change is persisted and returned on the next read.
2. [API] Given a signed-in member, when they submit a description longer than 1000 characters, then the response is 400 Bad Request and nothing is persisted.
3. [E2E] Given a member editing their profile, when they save, then a confirmation is shown without leaving the screen.

---

## L2-022: Restrict neighbourhood to the congregation's set
**Traces to:** L1-004

See also L2-002. A member's neighbourhood shall be one of their own congregation's
configured names.

**Acceptance Criteria:**
1. [API] Given a member of `St. Aidan's`, when they set their neighbourhood to a name configured only in `St. Mark's`, then the response is 400 Bad Request.
2. [E2E] Given a member editing their profile, when they open the neighbourhood control, then every option shown belongs to their congregation.

---

## L2-023: Declare help tags
**Traces to:** L1-004

A member shall be able to declare the kinds of help they are willing to offer, chosen from
the congregation's set, and these shall appear on their public profile and in the directory.

**Acceptance Criteria:**
1. [API] Given a signed-in member, when they select two help tags, then both are persisted and returned on their public profile.
2. [E2E] Given a member with help tags declared, when another member opens their profile, then those tags are shown.

---

## L2-024: View another member's public profile
**Traces to:** L1-004

A member shall be able to view another member's profile, showing their name, neighbourhood,
description, help tags, and current listings. Email addresses shall never appear.

**Acceptance Criteria:**
1. [API] Given two approved members of one congregation, when one requests the other's public profile, then name, neighbourhood, description, help tags, and active listings are returned.
2. [API] Given any member's public profile, when it is returned, then it contains no email address.
3. [E2E] Given a member viewing another's profile, when the screen loads, then that member's active listings are shown and each opens its listing.

---

## L2-025: Leave the congregation
**Traces to:** L1-004

A member shall be able to leave, which shall require confirmation, end their session, and
withdraw their active listings from the board.

**Acceptance Criteria:**
1. [API] Given a member with two active listings, when they leave the congregation, then neither listing appears on the board and their session is ended.
2. [E2E] Given a member on profile and settings, when they choose to leave, then a confirmation is required before the action proceeds.
3. [E2E] Given a member who cancels the confirmation, when the dialog closes, then they remain a member and their listings are unchanged.

---

## L2-026: Choose a listing kind before entering details
**Traces to:** L1-005

Posting shall begin by choosing Lend, Give, Sell, or Help, and the chosen kind shall
determine which detail form is presented. The kind shall not be silently defaulted.

**Acceptance Criteria:**
1. [E2E] Given a member posting a listing, when they open the post flow, then all four kinds are offered and no detail fields are shown.
2. [E2E] Given the kind chooser, when the member chooses Lend, then the Lend detail form is shown and it offers a return-by field.
3. [E2E] Given the kind chooser, when the member chooses Sell, then the Sell detail form is shown and it offers a price field.
4. [API] Given a listing submitted without a kind, when it is posted, then the response is 400 Bad Request naming the field.

---

## L2-027: Create a Lend listing
**Traces to:** L1-005

A Lend listing shall carry a title, description, category, neighbourhood, and the period
within which the owner expects the item back. It shall not carry a price.

**Acceptance Criteria:**
1. [API] Given a signed-in member, when they post a Lend listing with a title, description, category, neighbourhood, and return-by period, then it is created with kind Lend and appears on the board.
2. [API] Given a Lend listing submitted with a price, when it is posted, then the response is 400 Bad Request.
3. [E2E] Given the Lend form, when it is displayed, then no price field is present.

---

## L2-028: Create a Give listing
**Traces to:** L1-005

A Give listing shall carry a title, description, category, and neighbourhood, and shall be
marked as free with pickup arranged by the members. It shall not carry a price.

**Acceptance Criteria:**
1. [API] Given a signed-in member, when they post a Give listing with the required fields, then it is created with kind Give and no price.
2. [API] Given a Give listing submitted with a price, when it is posted, then the response is 400 Bad Request.
3. [E2E] Given a Give listing on the board, when it is displayed, then it is identified as being given away rather than sold.

---

## L2-029: Create a Sell listing
**Traces to:** L1-005

A Sell listing shall carry a title, description, category, neighbourhood, condition, and a
price in Canadian dollars. The price is a stated asking figure only; see L2-034.

**Acceptance Criteria:**
1. [API] Given a signed-in member, when they post a Sell listing with a price of 45.00, then it is created with kind Sell and that price.
2. [API] Given a Sell listing submitted without a price, when it is posted, then the response is 400 Bad Request naming the field.
3. [API] Given a Sell listing submitted with a negative price, when it is posted, then the response is 400 Bad Request.
4. [E2E] Given a Sell listing on the board, when it is displayed, then its price is shown.

---

## L2-030: Create a Help listing
**Traces to:** L1-005

A Help listing shall carry a title, description, category, neighbourhood, and one or more
availability windows. It shall not carry a price or a photo, because it offers time rather
than an object.

**Acceptance Criteria:**
1. [API] Given a signed-in member, when they post a Help listing with two availability windows, then it is created with kind Help and both windows are returned.
2. [API] Given a Help listing submitted with no availability window, when it is posted, then the response is 400 Bad Request.
3. [API] Given a Help listing submitted with a price, when it is posted, then the response is 400 Bad Request.
4. [E2E] Given a Help listing on the board, when it is displayed, then its availability is shown and no photo placeholder is present.

---

## L2-031: Validate listing input
**Traces to:** L1-005

Listing fields shall be bounded and validated, and errors shall name the field at fault.

**Acceptance Criteria:**
1. [API] Given a listing with a title longer than 120 characters, when it is posted, then the response is 400 Bad Request naming the title.
2. [API] Given a listing with an empty title, when it is posted, then the response is 400 Bad Request naming the title.
3. [API] Given a listing with a description longer than 4000 characters, when it is posted, then the response is 400 Bad Request naming the description.
4. [E2E] Given a member submitting an incomplete listing, when they submit, then each invalid field is marked and the first is focused.

---

## L2-032: Attach a photo to a goods listing
**Traces to:** L1-005

A Lend, Give, or Sell listing shall accept at most one image, of a permitted type and
bounded size. See L2-102 for upload safety.

**Acceptance Criteria:**
1. [API] Given a goods listing, when a JPEG of 2 MB is attached, then it is stored and returned with the listing.
2. [API] Given a goods listing, when a file of 12 MB is attached, then the response is 413 Payload Too Large and nothing is stored.
3. [API] Given a goods listing, when a file whose content is not a permitted image type is attached, then the response is 415 Unsupported Media Type.

---

## L2-033: Confirm that a listing is published
**Traces to:** L1-005

After posting, the member shall be shown that the listing is live and offered the ways
onward: view it, post another, or return to the board.

**Acceptance Criteria:**
1. [E2E] Given a completed listing form, when the member posts it, then a confirmation screen states the listing is on the board.
2. [E2E] Given the confirmation screen, when it is shown, then it offers to view the listing, post another, and return to the board.
3. [E2E] Given the confirmation screen, when the member chooses to view the listing, then the listing they just created is shown.

---

## L2-034: Do not collect payment when posting
**Traces to:** L1-005

A price on a Sell listing is a stated asking figure. The system shall not collect, hold, or
transmit payment at any point.

**Acceptance Criteria:**
1. [API] Given the published API surface, when it is enumerated, then no endpoint accepts payment instrument details.
2. [E2E] Given a Sell listing, when it is viewed, then the price is accompanied by a statement that payment is arranged directly between members.

---

## L2-035: List own active listings
**Traces to:** L1-006

A member shall be able to see their own active listings, each showing its kind, status, and
the number of open requests against it.

**Acceptance Criteria:**
1. [API] Given a member with three active listings, when they request their listings, then all three are returned with their kind, status, and open request count.
2. [E2E] Given a member with a listing carrying two open requests, when they open their listings, then the count is shown and leads to those requests.

---

## L2-036: Edit a listing
**Traces to:** L1-006

A member shall be able to change the details of their own listing. The edit screen shall be
distinct from the create screen in its heading and its action.

**Acceptance Criteria:**
1. [API] Given a member's own active listing, when they submit a changed title, then the change is persisted.
2. [API] Given a listing, when a member attempts to change its kind, then the response is 400 Bad Request and the kind is unchanged.
3. [E2E] Given a member editing their listing, when the screen loads, then it is headed as an edit, its fields are populated, and its action reads as saving rather than posting.

---

## L2-037: Close out a listing in the vocabulary of its kind
**Traces to:** L1-006

Closing out shall use the wording and resulting status belonging to the listing's kind:
Sell closes as sold, Give as given away, Lend as archived, Help as completed.

**Acceptance Criteria:**
1. [API] Given an active Sell listing, when its owner marks it sold, then its status becomes `Sold` and it no longer appears on the board.
2. [API] Given an active Give listing, when its owner marks it taken, then its status becomes `Given away`.
3. [API] Given an active Lend listing, when its owner marks it taken, then its status becomes `Archived`.
4. [API] Given an active Help listing, when its owner marks it booked, then its status becomes `Completed`.
5. [E2E] Given a member's own Sell listing, when they open its actions, then the close-out action reads `Mark as sold` and not a generic wording.

---

## L2-038: Archive a listing
**Traces to:** L1-006

A member shall be able to archive an active listing without closing it out, removing it from
the board while keeping it recoverable.

**Acceptance Criteria:**
1. [API] Given an active listing, when its owner archives it, then it no longer appears on the board and is returned among that member's archived listings.
2. [E2E] Given a member archiving a listing, when they confirm, then the archived list is shown containing that listing.

---

## L2-039: Restore or repost an archived listing
**Traces to:** L1-006

A member shall be able to return an archived listing to the board.

**Acceptance Criteria:**
1. [API] Given an archived listing, when its owner restores it, then its status becomes active and it appears on the board.
2. [E2E] Given a member viewing their archived listings, when they restore one, then it appears in their active listings.

---

## L2-040: Permanently delete a listing
**Traces to:** L1-006

A member shall be able to delete a listing permanently. Deletion shall require confirmation
and shall be irreversible.

**Acceptance Criteria:**
1. [API] Given an archived listing, when its owner deletes it, then a subsequent request for it returns 404 Not Found.
2. [E2E] Given a member deleting a listing, when they choose to delete, then a confirmation is required before it proceeds.
3. [E2E] Given the delete confirmation, when the member cancels, then the listing remains.

---

## L2-041: Restrict listing modification to its owner
**Traces to:** L1-006

A listing shall be modifiable only by the member who created it, or by a moderator acting
under L2-084.

**Acceptance Criteria:**
1. [API] Given a listing owned by another member of the same congregation, when a member edits it, then the response is 403 Forbidden and nothing changes.
2. [API] Given a listing owned by another member, when a member archives or deletes it, then the response is 403 Forbidden.
3. [E2E] Given a member viewing another member's listing, when the screen loads, then no edit, archive, or close-out action is present.

---

## L2-042: Display the board
**Traces to:** L1-007

The board shall show the active listings of the member's congregation, each carrying its
kind, title, owner, and neighbourhood, and each opening its listing.

**Acceptance Criteria:**
1. [API] Given a congregation with twelve active listings, when a member requests the board, then twelve listings are returned, each with kind, title, owner display name, and neighbourhood.
2. [API] Given a congregation with an archived listing, when a member requests the board, then that listing is absent.
3. [E2E] Given a member on the board, when they select a listing, then that listing's detail screen is shown.

---

## L2-043: Filter the board by kind
**Traces to:** L1-007

The board shall be filterable to a single kind, and the active filter shall be evident.

**Acceptance Criteria:**
1. [API] Given a board of mixed kinds, when it is requested filtered to Lend, then only Lend listings are returned.
2. [E2E] Given the board, when the member filters to Give, then only Give listings are shown and the Give filter is marked as current.
3. [E2E] Given a filtered board, when the member clears the filter, then listings of all four kinds are shown.

---

## L2-044: Convey a listing's kind without relying on colour
**Traces to:** L1-007

The board distinguishes kinds by colour. Colour shall never be the only carrier of that
information.

**Acceptance Criteria:**
1. [E2E] Given any listing on the board, when it is rendered, then its kind is present as text within the listing.
2. [E2E] Given the board rendered with colour removed, when a listing is inspected, then its kind remains determinable.

---

## L2-045: Show an empty board
**Traces to:** L1-007

A congregation with no active listings shall be shown an explanation and an invitation to
post the first one.

**Acceptance Criteria:**
1. [API] Given a congregation with no active listings, when a member requests the board, then an empty collection is returned with a 200 status.
2. [E2E] Given an empty board, when it loads, then it explains that nothing is posted yet and offers to post a listing.

---

## L2-046: Show the board loading
**Traces to:** L1-007

While the board is loading, its pending state shall be conveyed to assistive technology as
well as visually.

**Acceptance Criteria:**
1. [E2E] Given the board is loading, when the screen is inspected, then a live region announces that listings are loading.
2. [E2E] Given the board has loaded, when the screen is inspected, then the loading announcement is gone.

---

## L2-047: Show the board failing to load
**Traces to:** L1-007

If the board cannot be loaded, the member shall be told plainly and offered a retry.

**Acceptance Criteria:**
1. [E2E] Given the board request fails, when the screen renders, then it states that the board failed to load and offers to try again.
2. [E2E] Given the failure screen, when the member chooses to try again, then the board is requested again.

---

## L2-048: Search listings by text
**Traces to:** L1-008

A member shall be able to search the titles and descriptions of active listings in their
congregation.

**Acceptance Criteria:**

## L2-101: Minimise and erase personal data
**Traces to:** L1-015

Personal data shall be limited to what a feature needs, withheld from responses
describing other members, exportable on request, and erasable.

**Acceptance Criteria:**
1. [API] Given any endpoint returning another member, when its response is inspected, then it contains no email address.
2. [API] Given a member who leaves the congregation, when erasure is requested, then their profile, listings, and messages are removed or irreversibly anonymised within the documented period.
3. [API] Given a member, when they request an export of their data, then their profile, listings, requests, and messages are returned.

---

## L2-102: Handle uploaded files safely
**Traces to:** L1-015

An uploaded file shall be accepted only when its content matches a permitted image type,
and shall be re-encoded and stripped of embedded metadata before storage.

**Acceptance Criteria:**
1. [API] Given an uploaded file whose declared type differs from its content, when it is submitted, then it is rejected with 415 Unsupported Media Type.
2. [API] Given an uploaded image, when it is stored, then it is re-encoded and stripped of embedded metadata.
3. [API] Given an uploaded image, when it is served, then it is served from a path that cannot execute and with a Content-Type matching its content.

---

## L2-103: Meet API response time targets
**Traces to:** L1-016

The API shall meet stated 95th-percentile response times at the scale of a congregation.

**Acceptance Criteria:**
1. [API] Given a congregation of 500 listings, when the board is requested, then the 95th percentile response time is under 300 ms.
2. [API] Given a congregation of 500 listings, when a search is performed, then the 95th percentile response time is under 500 ms.
3. [API] Given any write endpoint under nominal load, when it is called, then the 95th percentile response time is under 500 ms.

---

## L2-104: Meet page weight and paint targets
**Traces to:** L1-016

The web client shall meet stated paint, layout-stability, and transfer-size targets.

**Acceptance Criteria:**
1. [E2E] Given the board on a simulated 4G connection, when it loads, then Largest Contentful Paint occurs within 2.5 seconds.
2. [E2E] Given the board, when it loads, then Cumulative Layout Shift is below 0.1.
3. [E2E] Given any screen, when its initial transfer is measured, then compressed JavaScript is under 300 KB.

---

## L2-105: Paginate long collections
**Traces to:** L1-016

A long collection shall be returned in bounded pages, each carrying a cursor for the
next.

**Acceptance Criteria:**
1. [API] Given a congregation with 500 listings, when the board is requested without a page parameter, then at most 50 are returned with a cursor for the next page.
2. [API] Given a cursor, when the next page is requested, then the following listings are returned without repeating any from the previous page.
3. [API] Given a page size above the documented maximum, when it is requested, then the maximum is applied rather than the requested value.

---

## L2-106: Serve images efficiently
**Traces to:** L1-016

A listing image shall be served at a size appropriate to its use, and images below the
fold shall load lazily.

**Acceptance Criteria:**
1. [API] Given an uploaded listing image, when it is requested at board size, then a resized derivative is served rather than the original.
2. [E2E] Given the board, when images below the fold are inspected, then they are lazily loaded.

---

## L2-107: Sustain many congregations concurrently
**Traces to:** L1-016

Response time targets shall continue to hold with many congregations active, and load in
one congregation shall not degrade another.

**Acceptance Criteria:**
1. [API] Given 50 congregations each with active members, when load is applied across all of them, then response time targets in L2-103 continue to hold.
2. [API] Given a single congregation generating heavy load, when other congregations are measured, then their response times are unaffected.

---

## L2-108: Lay out correctly across every viewport band
**Traces to:** L1-017

Every screen shall be correct at extra small (under 576px), small (576px and above), medium
(768px and above), large (992px and above), and extra large (1200px and above).

**Acceptance Criteria:**
1. [E2E] Given any screen at each of 375, 576, 768, 992, and 1200 pixels wide, when it renders, then no horizontal scrolling of the page body occurs.
2. [E2E] Given any screen at each band, when it renders, then no text is clipped and no interactive control is obscured.
3. [E2E] Given the board at 375 pixels, when it renders, then listings are readable in a single column.
4. [E2E] Given the board at 1200 pixels, when it renders, then at least three listings are shown per row.

---

## L2-109: Keep primary navigation reachable at every band
**Traces to:** L1-017

All five primary destinations shall be reachable at every viewport width. A destination shall
not exist only above a breakpoint.

**Acceptance Criteria:**
1. [E2E] Given any screen at 375 pixels, when navigation is inspected, then Board, Search, Post, Inbox, and You are all reachable.
2. [E2E] Given any screen at 1200 pixels, when navigation is inspected, then the same five destinations are present in the same order.
3. [E2E] Given any screen at any band, when the notification count is inspected, then it is reachable.

---

## L2-110: Meet touch target sizes
**Traces to:** L1-017

Every interactive control shall present a touch target of at least 44 by 44 CSS pixels,
or equivalent separating space.

**Acceptance Criteria:**
1. [E2E] Given any screen at 375 pixels, when every interactive control is measured, then each is at least 44 by 44 CSS pixels or separated by equivalent spacing.

---

## L2-111: Operate every screen by keyboard
**Traces to:** L1-017

Every screen shall be fully operable by keyboard in a logical order, shall offer a skip
link, and shall trap focus inside an open dialog.

**Acceptance Criteria:**
1. [E2E] Given any screen, when it is traversed by keyboard alone, then every interactive control is reachable and operable in a logical order.
2. [E2E] Given any screen, when the first tab is pressed, then a skip link to the main content is offered.
3. [E2E] Given an open dialog, when it is traversed by keyboard, then focus is trapped within it and Escape closes it, returning focus to the control that opened it.

---

## L2-112: Show focus visibly on every surface
**Traces to:** L1-017

Controls appear on white, cream, stone, and indigo fields; a focus indicator shall be
visible on all of them.

**Acceptance Criteria:**
1. [E2E] Given a control on each of the four field colours, when it receives keyboard focus, then a focus indicator is visible with a contrast ratio of at least 3:1 against its field.
2. [E2E] Given any focusable control, when it receives focus, then the indicator is not suppressed.

---

## L2-113: Meet contrast requirements
**Traces to:** L1-017

Text and interface components shall meet the WCAG 2.2 AA contrast minimums against their
backgrounds.

**Acceptance Criteria:**
1. [E2E] Given any body text, when its colours are measured, then the contrast ratio against its background is at least 4.5:1.
2. [E2E] Given any large text or interface component boundary, when measured, then the contrast ratio is at least 3:1.
3. [E2E] Given muted secondary text on the stone field, when measured, then the contrast ratio is at least 4.5:1.

---

## L2-114: Respect reduced motion
**Traces to:** L1-017

A client requesting reduced motion shall receive no entrance animation and no non-
essential transition.

**Acceptance Criteria:**
1. [E2E] Given a client requesting reduced motion, when the board loads, then no entrance animation runs.
2. [E2E] Given a client requesting reduced motion, when any transition would occur, then it is suppressed or reduced to an instantaneous change.

---

## L2-115: Expose correct semantics to assistive technology
**Traces to:** L1-017

Every screen shall expose correct landmarks, headings, image descriptions, form labels,
and current-page state to assistive technology.

**Acceptance Criteria:**
1. [E2E] Given any screen, when its structure is inspected, then it has one main landmark, a navigation landmark with an accessible name, and a single first-level heading.
2. [E2E] Given any image conveying meaning, when it is inspected, then it has an accessible description, and decorative images are hidden from assistive technology.
3. [E2E] Given any form control, when it is inspected, then it has a programmatically associated label, and validation errors are associated with their field.
4. [E2E] Given the current navigation destination, when it is inspected, then it is marked as current.

---

## L2-116: Expose a health endpoint
**Traces to:** L1-018

The system shall expose a health endpoint reporting the state of each dependency,
without disclosing configuration.

**Acceptance Criteria:**
1. [API] Given a running system with its dependencies available, when health is requested, then the response is 200 and names each dependency as healthy.
2. [API] Given an unavailable database, when health is requested, then the response is 503 and names the database as unhealthy.
3. [API] Given the health endpoint, when it is requested without credentials, then it returns a status without disclosing connection strings or versions.

---

## L2-117: Log with correlation
**Traces to:** L1-018

Every log entry arising from a request shall carry a correlation identifier, reusing one
supplied by the caller.

**Acceptance Criteria:**
1. [API] Given any request, when it is processed, then a correlation identifier is recorded on every log entry arising from it.
2. [API] Given a request carrying a correlation identifier, when it is processed, then that identifier is used rather than a new one.
3. [API] Given a handled failure, when it is logged, then the entry carries the correlation identifier, the endpoint, and the congregation identifier.

---

## L2-118: Emit operational metrics
**Traces to:** L1-018

The system shall expose request, error, and latency metrics for each endpoint.

**Acceptance Criteria:**
1. [API] Given traffic to the API, when metrics are scraped, then request count, error count, and latency distribution are exposed per endpoint.
2. [API] Given a rate-limited request, when metrics are scraped, then the rejection is counted.

---

## L2-119: Keep personal data out of telemetry
**Traces to:** L1-018

Telemetry shall carry no personal data, no message content, and no internal detail.

**Acceptance Criteria:**
1. [API] Given any log entry, when it is inspected, then it contains no email address, no message body, and no listing description.
2. [API] Given a validation failure, when it is logged, then the offending value is not recorded, only the field name.
3. [API] Given an error surfaced to a client, when it is inspected, then it contains no stack trace and no internal identifier.

---

## L2-120: Review my own requests
**Traces to:** L1-009

A member shall be able to see the requests they have made, each showing the listing, its
owner, the terms of the request, and its status, with a route to the message thread where a
request was accepted.

**Acceptance Criteria:**
1. [API] Given a member with three requests, when they request their own requests, then all three are returned with the listing, its owner, the terms, and the status.
2. [API] Given a member, when they request their own requests, then requests made by other members are absent.
3. [API] Given an accepted request, when the member's own requests are returned, then the row carries the identifier of the thread it opened.
4. [E2E] Given a member who has just sent a request, when they choose to see their own requests, then the new request is shown as pending.
5. [E2E] Given a declined request, when the member views their own requests, then its status is shown as declined and no thread is offered.
