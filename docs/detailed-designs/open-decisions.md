# Open design inputs

These entries preserve uncertainties and conflicts in the source requirements. `<TO SUPPLY>` identifies an unresolved value or decision. The feature designs remain complete about the affected paths and their dependencies; they do not claim an undecided policy is implemented. Source wording remains unchanged.

| ID | Requirement or boundary | Missing input or conflict | Design consequence |
|---|---|---|---|
| D-01 | `L2-010`, `L2-012`, `L2-085` | `<TO SUPPLY>`: email collection/verification and joining-reason capture. Joining asks for name and neighbourhood; sign-in requires an email and moderation requires a reason. | The joining transaction cannot be implemented from the established profile fields alone. Add explicit capture and verification criteria before completing that capability. Existing email uniqueness permits one membership per normalised address across the deployment; multi-congregation membership is not inferred. |
| D-02 | `L2-005`–`L2-011`, `L2-090` | `<TO SUPPLY>`: invite alphabet, length beyond the minimum six, issue lifetime, joining-capability lifetime, retry/recovery after capability expiry, and moderator contact destination. | Invite and joining Options have no invented production values. Conditional consumption remains specified independently of the values. Error bodies distinguish no condition beyond the required 404/410 status; expired/used copy shares a recovery path. |
| D-03 | `L2-001`–`L2-004`, `L2-022`, `L2-023` | `<TO SUPPLY>`: initial administrator bootstrap, slug normalisation/length, help-tag catalogue administration and limits, and handling removal/rename of neighbourhoods or help tags already referenced. | Configuration retains ordered choices and immutable unique slug. Schema and validation changes await policy for referenced choices; no free-text fallback bypasses the configured set. |
| D-04 | `L2-030`, `L2-036`, `L2-057` | `<TO SUPPLY>`: availability-window timezone/input representation, boundaries, overlap policy, and handling edits to requested windows. Sell condition vocabulary and otherwise unstated field bounds also need specification. | Help requests select a declared identifier and snapshot terms; writes revalidate membership in the listing. The design introduces a typed interval without choosing missing business rules. |
| D-05 | `L2-032 AC1/AC2`, `L2-096 AC2`, `L2-102`, `L2-106` | `<TO SUPPLY>`: reconcile a permitted 2 MB image with the universal 1 MB request-body ceiling. Define multipart exception, upload byte/pixel limits, full format allowlist, derivative sizes, and image processor. | The proposed image pipeline cannot satisfy both literal body limits. JPEG is required, a 12 MB upload is rejected, and exact intermediate limits remain open. SQL-backed bytes are an explicit proposed storage choice, not an existing implementation. |
| D-06 | `L2-093 AC1`, `L2-116 AC3` | `<TO SUPPLY>`: add the health endpoint to the public exceptions or change anonymous-health acceptance. | Existing `/health` is anonymous. The target follows explicit health acceptance while documenting its conflict with the literal public-route list. Refresh uses a refresh credential; joining/profile and data-rights paths use restricted credentials rather than anonymous business access. |
| D-07 | `L2-025`, `L2-101` | `<TO SUPPLY>`: erasure completion period, deletion versus anonymisation, retained relationship/content treatment, backups, export format/scope/size, departed-member identity recovery, and rejoining. | Leaving is immediately specified; erasure completion cannot have an invented deadline. Authored versus complete thread/request export scope requires explicit choice. No completion claim precedes all required stores. |
| D-08 | `L2-013`, `L2-017`, `L2-099` | `<TO SUPPLY>`: production email provider/adapter, bounded delivery and address-processing retry policy, statistical timing tolerance, general/source request rates, failed-invite threshold, window algorithm, and bucket capacity. | Public responses stay identical and do not depend on email delivery. The known address limit is five requests per 15 minutes. Other thresholds await explicit documentation and acceptance measurements. |
| D-09 | `L2-070`–`L2-075`, `L2-084` | `<TO SUPPLY>`: whether moderator-action notifications can be disabled. Removal explicitly notifies the owner, while preferences permit choosing kinds. | Default-enabled request/decision/message kinds are a documented design choice. Source writes and enabled notifications remain atomic; no silent override of moderator notification policy is introduced. |
| D-10 | `L2-073`, `L2-109`, `L2-115` | `<TO SUPPLY>`: whether “every/any screen” includes public signed-out and awaiting-approval pages for navigation and unread counts; treatment of multiple visible primary-navigation regions. | The authenticated shell supplies five destinations and a shared count. Public shells currently omit those destinations, and unread member data cannot be loaded anonymously. Fullscreen acceptance needs the intended screen set. |
| D-11 | `L2-097`, `L2-098`, `L2-100` | `<TO SUPPLY>`: confirm that encoded response text means JSON transport/text rendering while decoded values stay unchanged. Supply hosting topology, trusted proxy list, CSP, HSTS policy, signing-secret source, and key rotation. | The design preserves original text and never renders member HTML. HTTPS and document-response headers are verified at the deployed hosting boundary, not inferred from API tests. |
| D-12 | `L2-103`, `L2-104`, `L2-107` | `<TO SUPPLY>`: nominal request rate/concurrency, benchmark hardware, duration, warm-up/cache state, simulated-4G profile, and measurable tolerance for other congregations being “unaffected.” | Fixed p95/LCP/CLS/transfer targets remain exact. Bounded admission and projections are proposed mechanisms, not performance evidence. Strictly zero degradation is not asserted without a defined measurement. |
| D-13 | `L2-117`–`L2-119` | `<TO SUPPLY>`: correlation header syntax/length, operational scrape authentication and collector topology, telemetry retention/export capacity, and scope of the phrase “no internal detail.” | Logs retain only the correlation/endpoint/congregation fields explicitly required for diagnosis; metrics exclude unbounded identifiers; client errors contain neither internal identifiers nor stacks. |
| D-14 | `L2-080`, `L2-081`, `L2-083` | `<TO SUPPLY>`: reason/note bounds, re-report policy after resolution, and reporter privacy when the listing owner is also a moderator. | The target gives owner privacy precedence, withholds reporter identity from that owner in both surfaces, and lets other moderators review. A unique lifetime report per member/listing is a stated design choice until reopening is defined. |

The prior lifecycle design selected cascading permanent deletion of requests and conversations with their listing. This tree retains that design decision explicitly and extends cleanup to photos and subject notifications. `L2-040` alone does not mandate the cascade, so confirmation copy states the consequence. Ordinary close-out and archive preserve conversations.
